# שיעור 1.4 — Pointers ושרשראות של Pointers

**מודול:** יסודות · **יחידות מקור:** CS420 7 - Virtual Memory & Multilevel Pointers, Multi Level Pointers In Depth

## הרעיון בקצרה

**Pointer** הוא משתנה שהערך שלו הוא כתובת של נתון אחר. משחקים בנויים משכבות של אובייקטים שמצביעים זה על זה: המשחק מחזיק pointer לעולם, העולם ל-שחקן, השחקן לנשק. כדי להגיע לנתון בצורה ששורדת הפעלה מחדש, הולכים באותה דרך שהמשחק הולך: מתחילים מכתובת סטטית ועוקבים אחרי ה-pointers, אחד אחרי השני. לרצף הזה קוראים **pointer chain** או multilevel pointer.

## Pointer הוא סתם מספר

אין בזיכרון שום סימון מיוחד ל-pointer. אלה 4 בתים (בתהליך 32 ביט) או 8 בתים (ב-64 ביט) שבמקרה מכילים כתובת תקפה.

```
address       bytes          as 4-byte value
0x0058AC00    00 20 3F 0A    0x0A3F2000    <- looks like an address
0x0A3F2000    64 00 00 00    100           <- the value it points to
```

הפעולה "ללכת לכתובת ששמורה כאן ולקרוא מה שיש שם" נקראת **dereference**. בכתיבה מקובלת מסמנים אותה בסוגריים מרובעים: `[0x0058AC00]` פירושו "הערך שנמצא בכתובת `0x0058AC00`", כלומר `0x0A3F2000`.

איך מזהים pointer בתצוגת זיכרון? ערך שנראה כמו כתובת באזור של ה-heap או של module, ושאם הולכים אליו מוצאים נתונים הגיוניים. ב-64 ביט קל עוד יותר: שמונה בתים שמתחילים ב-`00 00 7F` או דומה.

## רמה אחת: בסיס ועוד offset

בשיעור 1.2 ראינו ששדה במבנה נמצא ב-offset קבוע מתחילתו. בשיעור 1.3 ראינו שהמבנה עצמו זז בין הפעלות, אבל יש משתנה סטטי שמחזיק את כתובתו. מחברים:

```
health address = [game.exe + 0x18AC00] + 0xEC
```

קוראים את זה מבפנים החוצה:

1. לוקחים את ה-base של `game.exe` ומוסיפים `0x18AC00`. מקבלים כתובת סטטית.
2. קוראים את הערך ששמור שם. זו הכתובת הנוכחית של מבנה השחקן.
3. מוסיפים `0xEC`. זו הכתובת של שדה החיים.

הטעות הקלאסית היא לחבר את ה-offset לפני ה-dereference. `[base + 0x18AC00] + 0xEC` ו-`[base + 0x18AC00 + 0xEC]` הן שתי כתובות שונות לגמרי.

## כמה רמות

במשחק אמיתי יש בדרך כלל כמה תחנות. למשל, התחמושת של הנשק הנוכחי:

```
game.exe + 0x18AC00   ->  pointer to Player
Player   + 0x364      ->  pointer to current Weapon
Weapon   + 0x14       ->  pointer to Ammo info
AmmoInfo + 0x0        ->  ammo in clip (the value)
```

ובכתיבה מקוצרת:

```
[[[game.exe + 0x18AC00] + 0x364] + 0x14] + 0x0
```

הכלל זהה בכל רמה: **קוראים pointer, מוסיפים offset, וחוזרים על זה.** ה-offset האחרון לא עובר dereference. הוא מוביל לכתובת של הערך עצמו.

בקוד, פונקציה כזו נראית כך (בגרסה שרצה בתוך התהליך עצמו):

```cpp
uintptr_t ResolveChain(uintptr_t base, const std::vector<unsigned>& offsets)
{
    uintptr_t addr = base;
    for (unsigned off : offsets) {
        addr = *(uintptr_t*)addr;   // dereference
        addr += off;                // then add the offset
    }
    return addr;                    // address of the final value
}

// usage: int* ammo = (int*)ResolveChain(moduleBase + 0x18AC00, {0x364, 0x14, 0x0});
```

כל הכתובות וה-offsets בשיעור הזה הם דוגמאות להמחשה. בכל משחק, ובכל גרסה שלו, הם שונים. במסלול 2 נלמד למצוא אותם.

## למה ה-offsets יציבים והכתובות לא

| מה | משתנה בין הפעלות? | למה |
|----|---------------------|-----|
| base של ה-module | כן | ASLR |
| כתובת של אובייקט ב-heap | כן | מוקצה מחדש בכל פעם |
| offset של משתנה סטטי בתוך ה-module | לא | נקבע בזמן הקומפילציה |
| offset של שדה בתוך struct | לא | נקבע בזמן הקומפילציה |

כל מה שנקבע בקומפילציה נשאר יציב עד שהמפתחים מוציאים גרסה חדשה. אחרי עדכון משחק ה-offsets עלולים לזוז, וזו הסיבה ש-trainers "נשברים" בעדכונים. הפתרון לזה, pattern scanning, מחכה במסלול 6.

## איפה שרשרת נשברת

- **Null pointer.** אחת התחנות מכילה 0, למשל כי השחקן עוד לא נכנס למשחק או שאין לו נשק ביד. dereference של 0 הוא access violation. בודקים כל תחנה לפני שממשיכים.
- **אובייקט שהוחלף.** השחקן מת ונוצר מחדש בכתובת אחרת. מי ששמר את הכתובת הסופית במקום לפענח את השרשרת מחדש כותב עכשיו לזיכרון של מישהו אחר.
- **שרשרת שעובדת במקרה.** כלים לחיפוש pointers מחזירים אלפי מסלולים, ורובם תקפים רק עד ההפעלה הבאה או עד השלב הבא. שרשרת טובה היא קצרה, מתחילה ב-module של המשחק עצמו, ושורדת הפעלה מחדש, טעינת שלב ומוות של הדמות.
- **32 מול 64.** בתהליך 64 ביט כל pointer הוא 8 בתים. קריאה של 4 בתים בלבד מחזירה חצי כתובת.

## תרגיל על נייר

נתון קטע הזיכרון הבא בתהליך 32 ביט, כשה-base של `game.exe` הוא `0x00400000`:

| כתובת | ערך (4 בתים) |
|--------|----------------|
| `0x00401000` | `0x02A00000` |
| `0x02A00010` | `0x02B50000` |
| `0x02A00020` | `0x00000019` |
| `0x02B50008` | `0x0000004B` |

פענחו את `[[game.exe + 0x1000] + 0x10] + 0x8`. מה הכתובת הסופית ומה הערך שבה?

פתרון: `game.exe + 0x1000` הוא `0x00401000`, ושם שמור `0x02A00000`. מוסיפים `0x10` ומגיעים ל-`0x02A00010`, ושם שמור `0x02B50000`. מוסיפים `0x8` ומקבלים את הכתובת הסופית `0x02B50008`. הערך שבה הוא `0x4B`, כלומר 75.

## מילון מונחים

| מונח | משמעות |
|------|--------|
| **Pointer** | משתנה שמחזיק כתובת של נתון אחר |
| **Dereference** | קריאת הערך שנמצא בכתובת שה-pointer מחזיק |
| **Static address** | כתובת במקום קבוע ביחס ל-module |
| **Pointer chain** | רצף של pointers ו-offsets מכתובת סטטית עד לערך |
| **Null pointer** | pointer שערכו 0, כלומר לא מצביע על כלום |
| **`uintptr_t`** | טיפוס ב-C++ שגודלו כגודל כתובת: 4 או 8 בתים |

## בדיקה עצמית

1. מה ההבדל בין `[A] + 0x10` לבין `[A + 0x10]`?
2. בשרשרת עם שלושה offsets, כמה פעולות dereference מבצעים?
3. למה offset של שדה בתוך struct לא משתנה בין הפעלות, אבל כן עלול להשתנות אחרי עדכון משחק?
4. השרשרת שלכם עובדת, ואז המשחק קורס בתפריט הראשי. מה הסיבה הסבירה?
5. מה שלושת הסימנים של שרשרת אמינה?

תשובות: (1) הראשון קורא את הכתובת ששמורה ב-A ואז מוסיף 16. השני קורא את מה ששמור 16 בתים אחרי A. (2) שלוש: אחת לפני כל offset. (3) הוא נקבע בקומפילציה. גרסה חדשה היא קומפילציה חדשה, ואולי נוספו שדות. (4) Null pointer: בתפריט עדיין אין אובייקט שחקן. (5) קצרה, מתחילה ב-module של המשחק, ושורדת הפעלה מחדש והחלפת שלב.
