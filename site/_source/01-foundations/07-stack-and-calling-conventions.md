# שיעור 1.7 — ה-Stack ו-Calling Conventions

**מודול:** יסודות · **יחידות מקור:** Calling Conventions For Reverse Engineering, Stack Pointers Explained - ESP vs EBP

## הרעיון בקצרה

כשפונקציה אחת קוראת לאחרת, שתיהן חייבות להסכים על כמה דברים: איפה נמצאים הפרמטרים, איפה חוזר ערך ההחזרה, ומי מנקה אחרי הקריאה. ההסכם הזה נקרא **calling convention**. אין הסכם אחד: יש כמה, והקומפיילר בוחר ביניהם. למה זה חשוב לנו? כי כדי להבין מה פונקציה במשחק מקבלת, וכדי לקרוא לה בעצמנו בהמשך הקורס, צריך לדעת באיזה הסכם היא משתמשת. טעות בהסכם נגמרת כמעט תמיד בקריסה.

## Stack frame: המרחב של פונקציה אחת

כל קריאה לפונקציה מקבלת אזור משלה על ה-stack, שנקרא **stack frame**. בתהליך 32 ביט הוא נראה כך אחרי פתיחת הפונקציה (`push ebp` ואז `mov ebp, esp`):

```
higher addresses
  [ebp+0x10]   third argument
  [ebp+0x0C]   second argument
  [ebp+0x08]   first argument
  [ebp+0x04]   return address     <- pushed by call
  [ebp]        saved ebp          <- pushed by the function
  [ebp-0x04]   first local variable
  [ebp-0x08]   second local variable
lower addresses                   <- esp points here
```

שני כללים שכדאי לזכור בעל פה:

- **`ebp` ועוד משהו הוא פרמטר. `ebp` פחות משהו הוא משתנה מקומי.**
- `esp` זז כל הזמן, עם כל `push` ו-`pop`. `ebp` נשאר קבוע לאורך הפונקציה, ולכן נוח להתייחס דרכו.

קומפיילרים מודרניים, ובעיקר ב-64 ביט, מוותרים הרבה פעמים על `ebp` ופונים לכול דרך `rsp`. ההיגיון זהה, רק ה-offsets נראים אחרת.

## ההסכמים של 32 ביט

| הסכם | פרמטרים | מי מנקה את ה-stack | איפה פוגשים אותו |
|------|----------|---------------------|-------------------|
| `cdecl` | על ה-stack, מימין לשמאל | הקורא | ברירת המחדל של C. פונקציות עם מספר פרמטרים משתנה כמו `printf` |
| `stdcall` | על ה-stack, מימין לשמאל | הפונקציה הנקראת | כל ה-Windows API |
| `thiscall` | `this` ב-`ecx`, השאר על ה-stack | הפונקציה הנקראת | מתודות של מחלקות ב-C++ |
| `fastcall` | שני הראשונים ב-`ecx` ו-`edx`, השאר על ה-stack | הפונקציה הנקראת | קוד שעבר אופטימיזציה |

בכל ההסכמים ערך ההחזרה חוזר ב-`eax` (ו-float ב-register של נקודה צפה).

"מימין לשמאל" פירושו שהפרמטר האחרון נדחף ראשון. כך הפרמטר הראשון יוצא הקרוב ביותר לראש ה-stack, ב-`[ebp+8]`.

## איך מזהים את ההסכם בקוד

מסתכלים על שני מקומות: מה קורה מיד **אחרי** ה-`call`, ואיך הפונקציה **מסתיימת**.

```
; cdecl: the caller cleans up
push 2
push 1
call add_numbers
add  esp, 8          ; two arguments * 4 bytes

; stdcall: the function cleans up
push 2
push 1
call AddNumbers      ; ends with:  ret 8
```

| מה רואים | מסקנה |
|----------|--------|
| `add esp, N` אחרי ה-`call` | `cdecl` עם N/4 פרמטרים |
| הפונקציה מסתיימת ב-`ret N` | `stdcall`, `thiscall` או `fastcall` עם N/4 פרמטרים על ה-stack |
| `mov ecx, ...` או `lea ecx, ...` ממש לפני ה-`call` | כנראה `thiscall`: זה ה-pointer לאובייקט |
| הפונקציה משתמשת ב-`ecx` ו-`edx` בלי לאתחל אותם | `fastcall` |

המקרה של `thiscall` חשוב במיוחד, כי רוב קוד המשחקים כתוב ב-C++. ה-`ecx` שנטען לפני הקריאה הוא האובייקט שעליו המתודה פועלת: השחקן, הנשק, העולם. כך מוצאים מבנים בלי לסרוק זיכרון בכלל.

## 64 ביט: הסכם אחד

ב-Windows של 64 ביט יש הסכם אחד לכולם, והוא פשוט יותר:

| מה | איפה |
|----|------|
| ארבעת הפרמטרים הראשונים | `rcx`, `rdx`, `r8`, `r9` (ל-float: `xmm0` עד `xmm3`) |
| פרמטר חמישי והלאה | על ה-stack |
| ערך החזרה | `rax` (ל-float: `xmm0`) |
| ניקוי ה-stack | הקורא |
| `this` במתודה של C++ | `rcx`, כפרמטר ראשון רגיל |

שני פרטים שמפתיעים בפעם הראשונה:

- **Shadow space.** הקורא חייב להשאיר 32 בתים פנויים על ה-stack מעל כתובת החזרה, גם אם כל הפרמטרים עוברים ב-registers. לכן כמעט כל פונקציה נפתחת ב-`sub rsp, 0x28` או דומה.
- **יישור.** ברגע ה-`call`, `rsp` חייב להתחלק ב-16. קוד שכותבים ביד ומפר את הכלל הזה קורס בהוראות SSE, במקום שנראה לא קשור בכלל.

ב-Linux וב-macOS של 64 ביט ההסכם שונה (System V): ששת הפרמטרים הראשונים עוברים ב-`rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`.

## Registers שמורים

ההסכם קובע גם אילו registers פונקציה רשאית לדרוס:

| סוג | 32 ביט | 64 ביט (Windows) |
|-----|--------|-------------------|
| **Volatile** — הפונקציה רשאית לדרוס | `eax`, `ecx`, `edx` | `rax`, `rcx`, `rdx`, `r8`–`r11` |
| **Non-volatile** — חייבים לחזור כפי שהיו | `ebx`, `esi`, `edi`, `ebp` | `rbx`, `rsi`, `rdi`, `rbp`, `r12`–`r15` |

זה ההסבר לסדרת ה-`push` בתחילת כמעט כל פונקציה ולסדרת ה-`pop` בסופה. וזה גם כלל ברזל לקוד שנזריק בעצמנו בהמשך: כל register ששינינו ואינו volatile חייב לחזור לערכו המקורי, אחרת המשחק ימשיך לרוץ עם ערך שגוי ויקרוס שורות רבות אחר כך.

## מילון מונחים

| מונח | משמעות |
|------|--------|
| **Calling convention** | ההסכם על העברת פרמטרים, ערך החזרה וניקוי ה-stack |
| **Stack frame** | האזור על ה-stack ששייך לקריאה אחת לפונקציה |
| **Prologue / Epilogue** | הוראות הפתיחה והסגירה של פונקציה |
| **Caller / Callee** | הפונקציה הקוראת, והפונקציה הנקראת |
| **`this`** | ה-pointer לאובייקט שעליו פועלת מתודה ב-C++ |
| **Shadow space** | 32 בתים שהקורא משאיר על ה-stack ב-64 ביט |
| **Volatile register** | register שפונקציה רשאית לדרוס בלי לשחזר |

## בדיקה עצמית

1. בפונקציה של 32 ביט, מה נמצא ב-`[ebp+0xC]`? ומה ב-`[ebp-4]`?
2. ראיתם שלושה `push`, אחריהם `call`, ואחריו `add esp, 0xC`. איזה הסכם זה וכמה פרמטרים?
3. פונקציה מסתיימת ב-`ret 8` ולפני הקריאה אליה נטען `ecx`. מה סביר שזה, וכמה פרמטרים יש לה?
4. בקוד 64 ביט, איפה הפרמטר השלישי? ואיפה ערך ההחזרה?
5. למה קוד מוזרק חייב לשחזר את `ebx` אבל לא את `eax`?

תשובות: (1) הפרמטר השני, והמשתנה המקומי הראשון. (2) `cdecl` עם שלושה פרמטרים. (3) `thiscall`: האובייקט ב-`ecx` ועוד שני פרמטרים על ה-stack. (4) `r8`, ו-`rax`. (5) `ebx` הוא non-volatile והקוד שמסביב סומך על כך שלא ישתנה. `eax` הוא volatile.
