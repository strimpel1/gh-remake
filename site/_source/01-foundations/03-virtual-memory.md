# שיעור 1.3 — Virtual Memory: מפת הזיכרון של תהליך

**מודול:** יסודות · **יחידות מקור:** CS420 6 - What is Virtual Memory, Windows Virtual Memory Explained

## הרעיון בקצרה

כל תהליך ב-Windows חי בתוך **מרחב כתובות וירטואלי** משלו. הכתובת `0x00400000` בתהליך אחד והכתובת `0x00400000` בתהליך אחר הן שני מקומות שונים לגמרי בזיכרון הפיזי. מערכת ההפעלה והמעבד מתרגמים בשקט כל כתובת וירטואלית לכתובת פיזית. מבחינתנו המשמעות היא שלוש שאלות שחוזרות בכל פרויקט: איפה הנתון נמצא במפה, מה מותר לעשות באזור הזה, ולמה הכתובת משתנה בכל הפעלה.

## למה בכלל וירטואלי

- **בידוד.** תהליך אחד לא יכול לקרוא או לדרוס זיכרון של אחר בטעות. כדי לגשת לזיכרון של תהליך אחר צריך לבקש במפורש ממערכת ההפעלה (על זה במסלול 4).
- **פשטות.** כל תוכנה מקבלת מרחב רציף ופרטי, ולא צריכה לדעת מה עוד רץ במחשב.
- **יעילות.** אותו קובץ DLL נטען פעם אחת לזיכרון הפיזי וממופה לתהליכים רבים. זיכרון שלא בשימוש יכול לעבור לדיסק.

גודל המרחב תלוי בסוג התהליך:

| תהליך | גודל כתובת | מרחב למשתמש | דוגמה לכתובת |
|-------|-------------|--------------|----------------|
| 32 ביט | 4 בתים | 2GB כברירת מחדל | `0x00F8A3C0` |
| 64 ביט | 8 בתים | 128TB | `0x00007FF6A1B23C40` |

שאר המרחב שייך ל-kernel, והתהליך לא יכול לגעת בו.

## עמודים והרשאות

הזיכרון מחולק ל-**pages** (עמודים) בגודל `0x1000` בתים, כלומר 4KB. לכל עמוד יש מצב והרשאות:

| הרשאה | משמעות | איפה פוגשים אותה |
|-------|--------|-------------------|
| `R` — Read | מותר לקרוא | קבועים, מחרוזות |
| `RW` — Read/Write | מותר לקרוא ולכתוב | משתנים, heap, stack |
| `RX` — Read/Execute | מותר לקרוא ולהריץ, לא לכתוב | קוד התוכנה |
| `RWX` | הכול מותר | נדיר בתוכנה רגילה. נפוץ בקוד שנוצר בזמן ריצה |

ניסיון לבצע פעולה שההרשאה לא מתירה גורם ל-**access violation**, והתהליך קורס. זו הסיבה שאי אפשר סתם לשנות הוראת Assembly בקוד של משחק: עמודי הקוד הם `RX`. קודם משנים את ההרשאה ל-`RWX` עם הפונקציה `VirtualProtect`, כותבים, ומחזירים את ההרשאה המקורית. Cheat Engine עושה את זה בשבילכם מאחורי הקלעים.

## מה יש במפה

כשמסתכלים על מפת הזיכרון של תהליך (Memory Regions ב-Cheat Engine, או Memory Map ב-x64dbg) רואים כמה סוגי אזורים:

| אזור | מה יש בו | הרשאות אופייניות |
|------|----------|-------------------|
| **Module** — ה-EXE וכל DLL | קוד ונתונים שנטענו מקובץ | לפי section |
| **Heap** | זיכרון שהתוכנה מקצה בזמן ריצה | `RW` |
| **Stack** | משתנים מקומיים וכתובות חזרה. אחד לכל thread | `RW` |
| אזורים פרטיים אחרים | הקצאות ישירות של התוכנה | משתנה |

כל module מחולק ל-**sections**:

| Section | תוכן | הרשאות |
|---------|------|---------|
| `.text` | הקוד המקומפל | `RX` |
| `.rdata` | קבועים ומחרוזות | `R` |
| `.data` | משתנים גלובליים וסטטיים | `RW` |

ההבחנה החשובה ביותר לקורס הזה היא בין שני סוגי נתונים:

- **נתון סטטי** יושב ב-`.data` של module. המיקום שלו ביחס לתחילת ה-module קבוע בכל הפעלה.
- **נתון דינמי** מוקצה ב-heap בזמן ריצה. הכתובת שלו שונה בכל הפעלה, ולפעמים בכל שלב במשחק.

מבנה השחקן הוא כמעט תמיד דינמי. לכן הכתובת שמצאתם אתמול ב-Cheat Engine לא עובדת היום.

## Base address ו-ASLR

הכתובת שבה module נטען נקראת **base address**. כתובת בתוך module כותבים בדרך כלל ביחס אליה:

```
game.exe + 0x18AC00
```

זה נוח כי **ASLR** (Address Space Layout Randomization) גורם ל-Windows לטעון כל module בכתובת אחרת בכל הפעלה. הכתובת המוחלטת משתנה, אבל המרחק מתחילת ה-module נשאר קבוע:

```
run 1:  game.exe base = 0x00400000  ->  game.exe+0x18AC00 = 0x0058AC00
run 2:  game.exe base = 0x00D20000  ->  game.exe+0x18AC00 = 0x00EAAC00
```

מכאן הכלל: **כתובת יציבה היא תמיד module ועוד offset**, ולא מספר מוחלט. המרחק הזה נקרא גם RVA (Relative Virtual Address).

## איך זה מתחבר

המשחק צריך למצוא את מבנה השחקן שלו בכל הפעלה, למרות שהוא ב-heap בכתובת אקראית. הוא עושה את זה בעזרת pointer: משתנה סטטי, במקום קבוע ב-module, שמחזיק את הכתובת הנוכחית של המבנה.

```
game.exe+0x18AC00  (static, always there)
        |
        v  holds the address 0x0A3F2000
0x0A3F2000  (heap, different every run)  ->  Player struct
```

אם נמצא את המשתנה הסטטי הזה, נוכל להגיע לשחקן בכל הפעלה בדיוק כמו שהמשחק מגיע אליו. זה הנושא של השיעור הבא.

## לראות את זה בעיניים

1. פותחים תוכנה כלשהי של 32 ביט ומצרפים אליה את Cheat Engine.
2. ב-Memory View בוחרים View ואז Memory Regions. עוברים על הרשימה ומזהים את ה-EXE, את ה-DLLs ואת האזורים הפרטיים.
3. רושמים את ה-base address של ה-EXE, סוגרים את התוכנה, פותחים שוב ובודקים אם הוא השתנה.
4. מוצאים עמוד עם הרשאת Execute ועמוד עם הרשאת Write. האם יש עמוד עם שתיהן?

## מילון מונחים

| מונח | משמעות |
|------|--------|
| **Virtual address** | כתובת בתוך המרחב הפרטי של תהליך |
| **Page** | יחידת זיכרון של `0x1000` בתים, עם הרשאות משלה |
| **Access violation** | קריסה בגלל גישה שההרשאות לא מתירות |
| **Module** | קובץ EXE או DLL שנטען לתהליך |
| **Section** | חלק של module עם ייעוד והרשאות משלו |
| **Heap** | אזור להקצאות דינמיות בזמן ריצה |
| **Stack** | אזור למשתנים מקומיים ולכתובות חזרה, אחד לכל thread |
| **Base address** | הכתובת שבה module נטען |
| **ASLR** | טעינת modules בכתובות אקראיות בכל הפעלה |
| **RVA** | מרחק מה-base address של module |

## בדיקה עצמית

1. שני תהליכים קוראים את הכתובת `0x00401000`. האם הם רואים את אותם בתים?
2. למה כתיבה ישירה לתוך `.text` גורמת לקריסה, ומה עושים כדי לכתוב שם בכל זאת?
3. מה ההבדל בין נתון סטטי לנתון דינמי, ואיזה מהם שורד הפעלה מחדש?
4. ה-base של `game.exe` הוא `0x00A10000`. מה הכתובת המוחלטת של `game.exe+0x2F40`?
5. למה כותבים כתובות כ-module ועוד offset ולא כמספר מוחלט?

תשובות: (1) לא. לכל תהליך מרחב משלו. ייתכן שהתוכן זהה אם זה אותו קובץ, אבל אלה מיפויים נפרדים. (2) העמודים הם `RX`. משנים הרשאה עם `VirtualProtect`, כותבים ומחזירים. (3) סטטי יושב במקום קבוע ב-module ושורד. דינמי מוקצה ב-heap ומשתנה. (4) `0x00A12F40`. (5) בגלל ASLR ה-base משתנה, והמרחק ממנו לא.
